# 供应雷达平台介绍说明

## 一、先说清楚：供应雷达是什么

供应雷达是面向供应链保供业务的决策工作台。

它不是一张单纯展示数据的“大屏”，也不是替代 SAP、ERP 或 MES 的业务系统。它做的是把分散在 SAP、采购行动表、供应商交付记录和外部行情里的信息，整理成一套能帮助业务人员判断“现在哪里有问题、问题有多严重、下一步该做什么”的工作页面。

如果用一句话概括：

> 把供应链数据变成可判断、可追踪、可执行的保供结论。

### 平台不是什么

- 不是 SAP 的替代品，业务原始数据仍以 SAP 为准。
- 不是生产排程系统，生产板块是供应侧 What-if 推演，不是正式生产工单。
- 不是自动采购系统，补货建议需要业务人员确认后再执行。
- 不是对外公开企业敏感数据的窗口，比赛版只使用部分脱敏、仅工厂 1501 的数据。

## 二、为什么需要供应雷达

传统做法通常是：

- 库存看 SAP；
- 到货看采购表；
- 供应商交付看另一张 Excel；
- 缺料风险靠人盯；
- 行情和资讯再从外部网站手工查；
- 汇总材料每次重新整理。

问题不是没有数据，而是数据分散、口径不统一、判断依赖个人经验，而且很难快速回答几个关键问题：

1. 今天最需要处理的是哪几项物料？
2. 哪些供应商虽然还在供货，但交付风险已经明显上升？
3. 现有库存还能撑几天？
4. 如果需求上涨或供应商再延迟，缺口会扩大多少？
5. 哪个补货建议应该优先执行？

供应雷达的目标，就是把这些问题的判断过程和依据放到同一个工作台里。

## 三、平台整体架构

平台采用“数据与展示分离”的架构，可以拆成三层：

### 1. 数据生产层

负责从源头获取和整理数据：

- SAP ZWM002：库存与库龄；
- SAP ME2L：采购计划与到货节奏；
- SAP MB51：实际收货记录；
- 采购断料行动清单；
- 安全库存、补货建议等派生字段；
- WorkBuddy 抓取的外部行情和资讯。

### 2. 标准数据层

计算脚本把不同来源的数据统一处理，生成：

```text
data/dashboard_data.json
```

这个 JSON 是前端唯一的数据标准接口。

页面只读取 JSON，不直接访问 SAP、Excel 或外部网站。这样数据和展示可以各自维护，不会因为页面样式变化而影响计算逻辑。

### 3. 展示与发布层

静态 HTML、CSS、JavaScript 和 ECharts 读取 JSON 后渲染页面。

发布流程：

```text
WorkBuddy 更新数据
→ Python 计算与校验
→ Git 提交数据
→ GitHub Actions 构建
→ GitHub Pages 发布
```

## 四、平台主要板块

### 1. 今日指挥中心

这是每天打开平台后的第一页，重点是“今天先看什么”。

主要内容：

- 风险物料数量；
- 未来 7 天预计缺料；
- 异常到货；
- 待处理任务；
- 风险分档分布；
- 今日重点任务表；
- AI 今日行动建议；
- 未来 14 天缺料时间轴。

它的作用不是把所有数据摊开，而是先告诉使用者：

> 今天最值得优先处理的对象是什么。

### 2. 物料供需与保供

这个板块回答“物料够不够、什么时候会缺、要不要补”。

包含：

- 供需总览；
- 缺口测算；
- 安全库存；
- 补货建议；
- 到货跟踪；
- ATP 可承诺量；
- 动态库存天数；
- 采购行动明细。

关键计算口径：

- 动态库存天数 =（当前可用库存 + 在途库存）÷ 平均日销量；
- ATP 承诺量 = max（可用库存 + 在途库存 - 安全库存，0）；
- 建议补货量 = max（再订货点 - 可用库存 - 在途库存，0）；
- 安全库存采用 P95 日销量、P95 到货天数和缓冲量口径。

需要特别说明的是：当前没有销售订单占用数据，因此平台里的 ATP 是“供应侧 ATP”，不是严格意义上的销售订单 ATP。

### 3. 供应商与仓储

这个板块回答“谁在供、供得稳不稳、货放在哪里、资金压了多少”。

包含：

- 供应商画像；
- 全国供应来源地图；
- 交付风险榜；
- 准时率、中位延迟、P90 延迟；
- 缺收货情况；
- 库存地点分布；
- 库存金额和库龄结构。

地图采用本地 GeoJSON / SVG 底图，不依赖在线地图接口，适合比赛演示和内网环境。

### 4. 生产协同与动态沙盘

这个板块是供应侧的模拟推演，不是正式生产计划。

可以调整：

- 推演周期；
- 需求倍数；
- 供应商延迟；
- 安全库存策略。

平台会重新计算：

- 推演日耗；
- 推演到货；
- 目标库存；
- 推演缺口；
- 覆盖天数；
- 受影响供应商；
- 补货方案比较。

生产板块的价值是：在不影响正式业务数据的前提下，回答“如果需求上涨 20% 或供应商再晚 7 天，会发生什么”。

### 5. 行业情报与市场洞察

WorkBuddy 每天抓取公开行情和资讯，写入：

```text
data/external_market.json
```

平台展示：

- 行情快照；
- 品类结构；
- 平均涨跌；
- 重点品种；
- 供应商动态；
- 政策和供应风险；
- 原文来源和链接。

外部行情只作为辅助判断，不替代企业内部真实采购价格和合同数据。

### 6. AI 智能协同

AI 板块不是独立于业务之外的聊天机器人，而是贯穿全站的任务执行与决策辅助中心。

包括：

- WorkBuddy 协同状态；
- AI 问答；
- 任务执行；
- 审批跟踪；
- 决策依据；
- 效果复盘。

当前 AI 回答基于本地数据和规则，不把企业真实数据发送到外部模型。比赛环境中重点展示 Agent 如何把“发现问题—形成建议—派发任务—追踪结果”串起来。

## 五、平台如何支撑日常工作

### 场景一：每天早上快速判断风险

打开今日指挥中心：

1. 先看严重档和优先档数量；
2. 再看今日重点任务 Top 5；
3. 点击任务行查看建议动作和依据；
4. 决定催货、补单、复核或继续观察。

### 场景二：判断某个物料为什么缺

进入物料供需板块，查看：

- 当前可用；
- 在途；
- 平均日耗；
- 覆盖天数；
- 安全库存；
- 再订货点；
- 建议补货量；
- 供应商和预计到货时间。

### 场景三：评估供应商交付风险

进入供应商板块：

- 看风险等级；
- 看准时率和中位延迟；
- 看缺收货；
- 看关联物料；
- 在地图上查看供应地域分布。

### 场景四：做保供方案讨论

进入生产协同与动态沙盘：

- 调整需求倍数；
- 调整供应商延迟；
- 比较基准、需求上涨和延迟情景；
- 判断缺口和补货规模变化。

## 六、数据口径和安全边界

比赛公开版固定规则：

```text
模式：competition
工厂：仅 1501
单位：kg
脱敏：是
工厂 1160：不进入公开页面
```

安全要求：

- 不提交 SAP 原始 Excel；
- 不提交 MB51、ME2L、消耗表；
- 不提交内部版 JSON；
- 不提交账号、Token、密钥；
- 不直接访问外部模型或在线地图接口；
- 公开数据必须经过校验脚本检查。

## 七、两个项目的分工

### 供应雷达自动化

负责 SAP 抓取、翻译、脱敏、MB51 合并和计算基础数据。

### 供应链可视化平台

负责 JSON 生成、数据校验、页面渲染、离线分享版构建和 GitHub 发布。

### WorkBuddy

负责每日外部行情、定时执行脚本、校验数据并推送公开数据。

## 八、当前已知限制

为了避免误解，需要同步几个限制：

1. 当前 ATP 是供应侧 ATP，没有扣减真实销售订单占用。
2. 当前生产板块是供应侧推演，不是 MES 生产工单。
3. 当前历史快照尚未完整接入，部分“风险变化”仍显示为待接入。
4. MB51 存在缺收货记录时，会影响供应商准时率解释，不能直接等同于供应商责任。
5. 外部行情来自公开资讯，只作为辅助信号，不替代正式采购价格。
6. 比赛版只展示工厂 1501 的部分脱敏数据，内部全量版需单独部署和授权。

## 十、总结

供应雷达的核心价值不是“把页面做好看”，而是建立一套稳定的供应链保供工作机制：

- 数据从 SAP 和外部行情自动进入；
- 计算口径统一在 Python 脚本中；
- 前端只消费标准 JSON；
- 风险和建议都能下钻到依据；
- WorkBuddy 负责每日协同；
- GitHub Actions 负责自动发布；
- 比赛版与内部版有清晰的数据边界。

一句话总结：

> 供应雷达把“看数据”变成“做判断”，再把判断变成“可执行、可追踪的保供行动”。
